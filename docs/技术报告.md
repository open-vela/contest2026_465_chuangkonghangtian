## 2、摘要

（300 字以内）

本作品面向青少年与高校火箭/探空模型团队的遥测需求，构建"箭载 + 地面"双端遥测系统。箭载端以 ESP32-S3 采集 GPS、气压温度、六轴姿态，通过 LoRa 将数据实时下传，同时写入 microSD 卡并驱动无源蜂鸣器给出阶段确认音；地面端基于 openvela（NuttX）在思澈 SF32LB52 上实现 390×450 AMOLED 中文遥测大屏、双物理按键任务状态机，以及本地雷达相对位置解算，并通过 USB CDC 向电脑网页输出遥测与雷达数据。系统全程无云依赖，弱网/断链时地面端仍可本地完成姿态、距离、方位计算与显示。开发过程中定位并修复了 SPI 总线争用、串口复位、引脚复用缺失、行缓冲截断、控制台死锁、SD 引脚误配、SD 驱动寻址错误、SD 忙等拖死主循环等 11 类真实工程问题，地面端连续运行 90 秒零异常。

## 3、正文

### 3.1 绪论

**项目背景与问题定义**

火箭模型、探空火箭与高校研制的飞行器在飞行试验中，最核心的需求是**实时掌握飞行状态**：是否离架、姿态是否稳定、当前高度与速度、落点方位。现有方案存在三类痛点：

1. **商用遥测设备昂贵**：专业遥测电台与地面站动辄数万元，青少年团队与高校社团难以承担。
2. **依赖手机/云端**：部分方案把数据送到手机 App 或云平台，一旦断网或信号弱，飞行关键数据即丢失，无法用于现场回收决策。
3. **数据链路单向**：多数低成本方案只能箭载→地面单向传输，地面端无法向箭载下达指令（如分段记录、点火确认、异常中止）。

**技术难点**

1. **一对半双工 LoRa 模块同时承载遥测下传与指令上传**，必须解决收发冲突，否则按键指令会被自身发射淹没。
2. **异构双端协同**：箭载端跑 MicroPython，地面端跑 openvela（NuttX / C），两端需要在无中间件的条件下约定可靠协议。
3. **弱网与断链降级**：断链期间必须保证地面端不崩、不误判、可视化不中断。
4. **资源受限下的实时性**：地面端要同时驱动 390×450 AMOLED、触摸、按键、串口双向收发与本地解算，帧率与响应延迟需同时达标。

**创新点**

1. **地面端本地解算雷达**：以地基站为原点、正北向上的雷达盘，实时显示火箭的相对方位、地面投影距离、直线距离与相对高度。全部解算在 SF32 本地完成，不占用 LoRa 带宽。
2. **地基基准自动校准**：发射前火箭静置于发射点，箭载 GPS（1~3 m 精度）坐标即发射点坐标，地面端在待命阶段自动以箭载坐标为基准并做滑动平均，点火后冻结，省去人工录入。
3. **指令通道与遥测通道的时隙协调**：为半双工 LoRa 设计固定接收窗口 + 指令重复队列 + 音效抢占调度，使按键命令在强干扰下仍可靠到达。
4. **任务阶段音效语义化**：将任务阶段映射为五种可区分音效（确认长鸣 / 点火五声 / 灭火两声 / 结束四声递降 / 回待命上扬），操作者凭听觉即可确认指令已送达箭载端。

### 3.2 系统方案设计

**系统总体架构**

```
┌────────────────────────┐   LoRa 9600bps   ┌──────────────────────────┐
│ 箭载端 ESP32-S3         │ ───────────────→ │ 地面端 SF32LB52 (openvela)│
│ · GPS   NMEA 0183      │                  │ · CO5300 AMOLED 390×450  │
│ · MPU6050 姿态          │ ←─────────────── │ · 双按键状态机            │
│ · BME280 气压/温度       │  按键命令+音效     │ · 雷达本地解算            │
│ · LoRa DX-LR22         │                  │ · 中文界面/曲线页          │
│ · microSD CSV 记录      │                  │ · USB CDC 遥测输出        │
│ · 无源蜂鸣器             │                  └────────────┬─────────────┘
└────────────────────────┘                               │ USB 1Mbps
                                                          ↓
                                            ┌──────────────────────────┐
                                            │ 网页遥测大屏              │
                                            │ · 股票式十字光标曲线       │
                                            │ · 雷达扫描图 + 悬停详情    │
                                            └──────────────────────────┘
```

**方案论证与选型**

| 环节 | 选型 | 理由 | 备选方案对比 |
|---|---|---|---|
| 地面端主控 | 思澈 SF32LB52 + openvela | 赛事平台；自带 CO5300 AMOLED 与触摸；开源 NuttX 便于板级驱动改造 | 树莓派：成本高、启动慢、无低功耗优势 |
| 箭载端主控 | ESP32-S3 | 自带 WiFi/BLE 便于后续扩展；MicroPython 迭代快；UART/I2C 资源充足 | STM32：开发周期长，调试成本高 |
| 无线链路 | LoRa DX-LR22 @9600 | 低功耗、绕射能力强，空旷环境可覆盖数公里 | 2.4G 模块：距离不足；4G：依赖基站 |
| 显示 | 板载 AMOLED 390×450 | 分辨率高，适合多曲线与雷达盘 | 外接 I2C OLED：分辨率仅 128×64，雷达盘过小 |
| 端/云职责 | **全端侧**，无云依赖 | 断网可用；现场无网络环境仍能工作 | 云端解算：断网即失效 |

**端/云职责划分与降级策略**

- 全部采集、解算、显示均在端侧完成，不依赖任何云端服务。
- **断链降级**：地面端检测到超过设定时间无遥测后，自动标记 LoRa 断开、清零卫星数与时间，界面保留最后有效值并给出明确提示，不显示伪造数据。
- **定位缺失降级**：无 GPS 定位时，速度与高度由箭载端气压高度 + 加速度积分提供；地基基准未校准时，雷达盘直接显示"火箭方位"而非空白。

**关键模块设计**

1. **箭载端（ESP32-S3 + MicroPython）**：单循环多任务调度，采集与解析按固定周期执行，LoRa 发送按优先级分快包（姿态）/ 完整包（全量）+ 纯接收窗口。
2. **地面端（SF32LB52 + openvela/NuttX）**：四层结构——板级驱动层（LCD / 触摸 / 按键 / 串口）、显示层（framebuffer + 中文点阵）、业务层（状态机 / 融合 / 雷达解算）、通信层（LoRa 命令队列 + USB CDC 输出）。
3. **网页端**：零依赖单文件 HTML，通过 Web Serial 读取地面端 USB CDC 输出，Canvas 绘制多曲线与雷达盘。

### 3.3 核心算法与技术原理

**关键机制设计**

**(1) 半双工 LoRa 的收发时隙协调**

模块半双工，连续发射会完全阻塞接收。设计为：

```
每 2 秒周期内：留出 1 秒纯接收窗口，其余时间发射遥测
地面端指令：进入非阻塞重复队列，跨约 1.6~2 秒重发 10~20 次
箭载端去重：同一条音效命令 2.5 秒内只执行一次，其余仅回执
```

实测证明：窗口过短（400 ms）时指令完全收不到；改为 1 秒窗口后，箭载端可稳定收到并回执 `A:<命令>`。

**(2) 箭载端姿态与高度解算**

- 俯仰/横滚：加速度计重力分量反算 `pitch=atan2(ay,az)`、`roll=atan2(-ax,√(ay²+az²))`
- 偏航：MPU6050 无磁力计，采用陀螺仪 Z 轴角速度积分，并加入静止回零抑制漂移
- 高度：无定位时用气压相对高度；有定位时以气压相对变化叠加 GPS 海拔基准

**(3) 地面端雷达相对位置解算（本项目核心）**

以地基站为原点，正北为 0°：

```
水平距离  d = 2R·atan2(√a, √(1-a))，a = sin²(Δφ/2)+cosφ₁cosφ₂sin²(Δλ/2)   （haversine）
方位角    θ = atan2(sinΔλ·cosφ₂, cosφ₁sinφ₂ - sinφ₁cosφ₂cosΔλ)
相对高度  Δh = h_rocket - h_ground
直线距离  D = √(d² + Δh²)
```

工程要点：
- **精度保护**：经纬度传输采用 6~7 位小数，地面端用 `double` 解析（`float` 只有约 7 位有效数字，经度会丢约 1 m 精度）
- **地基基准自动校准**：待命阶段以箭载坐标做 30 点滑动平均作为地基基准，点火后冻结
- **静止平滑**：静止时 GPS 误差以随机噪声为主，平均后按 √N 降低

**(4) 中文显示实现**

思澈板级环境无中文字库，自制 16×16 点阵字库 `cn_font.h`（73 字，UTF-8 三字节索引），配合 `text_cn()` 绘制函数，实现阶段名、状态、刻度标签中文显示。

**openvela 系统能力的运用**

| 能力项 | 落地情况 |
|---|---|
| **图形** | 深度使用。framebuffer 直绘（`/dev/fb0` + `FBIO_UPDATE`）、AMOLED 面板驱动、自绘图表与雷达盘、中文点阵渲染 |
| AI | 未在端侧落地（本赛道为 AI 硬件产品创新，端侧模型非必须） |
| 多媒体 | 未落地（蜂鸣器提示音由箭载端承担） |

**对 openvela / NuttX 的适配与改进**

1. **板级驱动扩展**：`/dev/buttons` 原驱动仅支持 1 个按键（`NUM_BUTTONS=1`），扩展为双按键（KEY1=PA34 / KEY2=PA11），并在 `bsp_pinmux.c` 补齐 PA34 缺失的引脚复用配置。
2. **串口设备注册**：设备按注册顺序生成 `/dev/ttySx`，理解该机制后通过启用 UART3 获得 `/dev/ttyS1` 备用串口。
3. **构建系统经验**：`.config` 手工追加配置不会触发 `config.h` 重新生成，需重新执行 configure；该问题已记入 Skill 供后续复用。


| 外设 | 引脚 |

**应用 / 交互端设计**

- **地面端 UI（思澈 390×450 AMOLED，共 6 页，触摸左右滑动切换）**

  每页统一有页眉：页名 + 页码（如"3/6"）。各页内容如下：

  | 页 | 名称 | 页面内容 | 对应实现 |

  | 4 | 姿态 | 人工地平线姿态仪表、俯仰/滚转/偏航数值与姿态条 | `draw_page_att()` |
  | 5 | 火箭 | 火箭状态大字页：倾斜角、轴向加速度、高度速度主参数 | `draw_page_rocket_big()` |
  | 6 | 雷达 | 以地基站为原点、正北向上的雷达盘：同心距离环、火箭方位点、地面投影距离/直线距离/方位角/相对高度；含"校准地基"触摸按钮 | `draw_page_radar()` |

  曲线与刻度全部由 `framebuffer` 直绘，中文标签使用自制 16×16 点阵字库。

- **箭载端 TFT（ESP32-S3 板载 ST7735，160×128，6 行固定版面）**

  | 行 | 内容 |
  |---|---|
  | 1 | 标题 `TELEMETRY`（白） |
  | 2 | `G:FIX SAT16` —— 定位状态与卫星数（定位成功绿、未定位红） |
  | 3 | `ALT  123.4m V   4.5` —— 融合高度与速度 |
  | 4 | `BAR 1013.2hPa` —— 气压（hPa，便于与气象数据对照） |
  | 5 | `TMP   26.6C` —— 温度 |
  | 6 | `SD:0 REC 12:34:56` —— SD 记录状态三态：`SD:0 REC`（正在记录，绿）/ `SD:-- NO CARD`（未检测到卡，灰）/ `SD:0 stop`（已停止） |

  箭载端屏幕只显示自身可独立获得的信息，不显示 LoRa 链路判据（该判据在地面端更可靠），便于现场快速判断"采集是否正常、有没有在记录"。

- **网页端 UI**：股票软件风格——十字光标 + 坐标提示框、自适应网格数值、第二页三姿态/三加速度/高度/速度/气压曲线、雷达扫描盘（同心距离圆盘 + 扫描线 + 悬停详情）。
- **按键交互**：KEY2=点火确认/灭火，KEY1=点火/任务结束；阶段即时切换（本地，无无线延迟）。

**开发过程中定位并修复的问题（真实记录）**

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 板载 TFT 卡在开机画面 | SD 卡初始化复用硬件 SPI2，把 TFT 写数据重定向到 SD 引脚 | SD 改用 `SoftSPI` |
| 2 | 地面端 LCD 不亮 | 串口 RTS 拉高把 SoC 压在复位状态，面板初始化失败 | 打开串口后显式拉低 RTS/DTR |
| 3 | 按键只有待命阶段有反应 | `bsp_pinmux.c` 中 PA34 引脚复用被注释，KEY1 无任何事件 | 补上 `HAL_PIN_Set(PAD_PA34, GPIO_A34, PIN_PULLDOWN, 1)` |
| 4 | 火箭坐标始终为 0 | 增加经纬度字段后完整包约 142 字节，超出 128 字节行缓冲被截断 | 行缓冲扩到 256 字节 |
| 5 | 点"获取定位"后板子卡死 | 地面端读 stdin 与 NSH 争抢同一控制台导致死锁 | 移除 stdin 读取，改本机计算 |
| 6 | 运行约 24 秒后必卡死 | 卫星串口设备轮换反复 `close/open /dev/console` | 固定单设备并移除轮换 |
| 7 | 点火音延迟数秒 | 确认音重发阻塞了点火命令入队 | 新阶段音效抢占旧重发队列 |
| 8 | 坐标精度只有约 1 m | 发送 5 位小数 + 地面端用 `float` 解析 | 改 6~7 位小数 + `double` 解析 |
| 9 | SD 卡完全识别不到 | 代码引脚常量（`45/21/14/48`）与实物接线（`CS=14/SCK=21/MOSI=47/MISO=4`）不符，且 MOSI/MISO 一度接反；MISO 又曾接在板载 WS2812 RGB 灯的数据脚上，灯把 SPI 数据当颜色吃掉、同时其输入级拖累信号 | 用"固定 CS/SCK、遍历 MOSI×MISO 组合看 CMD0 是否回 0x01"的方式定位；MISO 挪到空闲 GPIO4 并把该脚让给 RGB 指示灯 |
| 10 | SD 卡初始化报 `timeout waiting for response` / 挂载报 `read error` | 上游 `sdcard.py` 三处缺陷：① 读 CSD 的 CMD9 未带 `release=False`，读完 R1 就拉高 CS，卡中止了随后的 CSD 数据块；② v2 分支一律按块寻址（`cdv=1`），而本卡 OCR 的 CCS=0 属 SDSC，必须按字节寻址（`cdv=512`），0 号块碰巧两种寻址都是 0 所以"看起来能读"；③ 等卡结束内部编程用的是**无上限忙等** `while spi.read(1,0xFF)[0]==0: pass` | ①② 分别改为 `release=False`、按 OCR 的 CCS 位决定 `cdv`；③ 给忙等加 0.8 秒上限，超时抛错交由上层统计并关闭 SD 记录；另把 `SDCard()` 默认的 1.32 MHz 显式降到 SoftSPI 跑得动的 400 kHz、给 MISO 加内部上拉 |
| 11 | **整个系统卡死**：串口无输出、LoRa 收发全停、屏幕不刷新 | 上面第 ③ 条：卡一旦进入坏状态，`sdcard.py` 的忙等永远出不来，主循环被彻底占住（实测用 Ctrl-C 抓到栈正好停在 `log_row → sd_flush → sdcard.write`）。写卡本身也慢：单次落盘 1.1 秒，而当时"缓冲滞留 1 秒就落盘"的规则还让每批只剩 1 行，等于把 80% 的主循环时间交给 SD | ① 忙等加超时（第 10 条）；② 落盘只攒批触发 + 只在接收窗口外写；③ **自适应节流**：单次落盘超过 600 ms 就自动把采样率逐级下调（最高 0.125 Hz），卡恢复后再自动调回；④ 初始化重试 6 次。改后实测主循环恢复正常：100 秒内 STAT 打印 10 条、遥测 2.5 包/秒、零写错误 |

**AI 工具对开发效率的提升**

本项目的 AI 协作方式以"**现象 → 假设 → 用日志/串口证伪 → 最小改动验证**"为主线，AI 主要承担三类工作：

1. **跨平台知识检索**：openvela/NuttX 的引脚复用表、串口设备注册规则、Kconfig 生成机制等资料分散，AI 快速定位到 `bf0_pin_const.c`、`sifli_uart.c` 等关键文件。
2. **日志驱动排错**：把串口原始输出交给 AI 分析，例如从"经纬度恒为 0 但卫星数正常"推断出"GGA 被解析、RMC 未解析"，进而定位到行缓冲长度问题。
3. **批量代码改造**：中文点阵字库生成、6 页 UI 布局调整、网页曲线绘制等重复性工作中显著提速。

**遇到的问题与解决方式**

- **AI 也会给错方向**：曾把"屏幕黑屏"误判为固件问题，实际是串口 RTS 电平。后期改为**先取证再修改**，每次改动都保留可复现的串口日志。
- **经验固化**：把 11 类真实问题沉淀进自定义 Skill，使同类问题在后续不再重复排查。

### 3.7 总结与展望

**成果总结**

完成了一套**无云依赖、双端协同**的火箭遥测原型系统：

- 箭载端实现 GPS（实测 16 星）、气压温度、六轴姿态采集，LoRa 实时下传约 4.3 包/秒，支持 SD 卡 CSV 记录（实测 331 行）、五种阶段音效与板载 RGB 阶段指示
- 地面端在 openvela 上实现 390×450 中文遥测大屏（6 页）、双按键任务状态机、半双工指令通道，以及本地雷达相对位置解算
- 网页端实现股票式多曲线大屏与雷达扫描盘
- 连续运行 90 秒零异常，全链路端到端验证通过

**应用前景与商业价值**

- **目标受众**：青少年航天科普社团、高校探空火箭队、模型火箭爱好者；年龄以 15~25 岁学生为主，地域集中在有航天社团的高校与科技特色中学。
- **使用偏好**：预算敏感（整套硬件目标控制在千元以内）、要求现场可用（野外无网络）、希望有直观可视化。
- **商业模式**：以开源硬件 + 开源软件（Apache 2.0）建立社区，通过**套件销售**（箭载板 + 地面站 + 传感器模块）与**培训课程包**变现；后续可扩展至无人机、气象探空、农业遥感等需要"低成本实时遥测 + 本地解算"的场景。
- **规模化潜力**：核心器件均为通用模块，易于量产；开源协议有利于被更多学校直接采用。

**不足与未来工作**

1. **SD 卡仍偶发初始化失败**：偶见 ACMD41 不就绪（卡无法完成内部初始化），已加 6 次重试缓解，但仍非 100% 成功；疑与 TF 模块供电余量和杜邦线接触质量有关，换用 Class 10 卡并就近加 100µF 去耦电容应能根治。此外这张 1 GB 老卡写卡很慢（单次落盘 220 ms~1.1 秒不等），代码已做自适应节流保证不影响 LoRa 收发，但代价是记录密度会随卡速自动下调。
2. **GPS 精度受硬件限制**：当前为民用单频模块（1~3 m），如需厘米级需引入 RTK 双模块方案。
3. **地面端无网络能力**：SF32LB52 无 WiFi 硬件，后续计划外接 ESP8266 模块（NuttX 自带 `NETUTILS_ESP8266` 驱动，默认串口即 `/dev/ttyS1`），实现天气查询与 AI 对话的**脱离电脑独立运行**。
4. **语音交互**：I2S 的 LRCK 引脚在现有排针上被触摸 I2C 占用，需权衡取舍；短期可先在网页端用浏览器语音能力实现。
5. **音频提示音位置**：目前蜂鸣器在箭载端，按键音效受无线时延影响；后续可在箭载端增加更多语义化音效或改用语音播报。
